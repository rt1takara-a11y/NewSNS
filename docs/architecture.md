以下は当初の設計メモ。

まず少人数（20〜30人）で検証するための、扱いやすい構成を目指す。
最初から自分でサーバーを借りて管理する必要はない。

## 役割ごとに必要なもの

| 役割 | 必要なもの |
|---|---|
| 画面とアプリの処理 | Webアプリを動かすホスティング |
| ログイン | 認証サービス（メールログイン） |
| 投稿やユーザー情報の保存 | データベース |
| 毎週のリセット | DB時計から週境界を算出。物理削除だけを保守ジョブで実行 |

少人数向け初期版なら、**ホスティング1つ ＋ 認証付きデータベース1つ**にまとめる方針が扱いやすい。
具体的なサービス名と料金は、構成を決める段階で最新の無料枠・利用条件を確認して選ぶ。
現段階で「完全無料で運営できる」とは断言しない。

> 補足: iPhone/Android のネイティブアプリは作らない。**スマホのブラウザで使えるWeb版**にすることで、初期の開発コストを抑える。

## データの分け方（サービス選び以上に重要）

このSNSの肝は、データを「継続する情報」と「週ごとの情報」に明確に分けること。

### 継続する情報（リセットで消えない）

- 内部アカウント（内部ID）
- 認証（メール）との対応
- 利用停止状態
- 通報対応に必要な管理記録

### 週ごとの情報（毎週月曜0:00に切り替わる）

- 公開プロフィール（名前・アイコン）
- 公開ID（毎週新しく発行）
- 投稿
- フォロー
- いいね
- 返信

### 設計上の鉄則

- **公開情報に内部IDを出さない。** 画面・URL・APIレスポンスのどこにも内部IDを露出しない。
- **毎週新しい公開プロフィールを作る。** 週ごとの公開IDで、その週のプロフィール・投稿・関係をひも付ける。
- **「画面から消す処理」と「運営が保持する記録の削除処理」は分けて設計する。** 通報対応のため一部の記録は保持しつつ、利用者から見える投稿は消す、という二層構造。

## データモデルの素案（イメージ）

> 具体的なテーブル定義は実装フェーズで確定する。ここは方向性のメモ。

- `accounts`（継続）: internal_id, email(認証と対応), status（active/suspended）, created_at
- `profiles`（週ごと）: public_id（毎週発行）, internal_id(FK, 非公開), period（例: 2026-W39）, display_name, icon
- `posts`（週ごと）: public_id 投稿者, period, body, created_at
- `follows` / `likes` / `replies`（週ごと）: いずれも public_id と period で表現
- `reports`（管理）: 通報記録。保持ポリシーは別途定義

※ `internal_id → public_id` の対応表は運営（DB内部）だけが持ち、公開面には一切出さない。

## セキュリティ・秘密情報

- パスワード・APIキーなどの秘密情報は**環境変数**で管理し、GitHubには絶対に入れない。
- 開発環境と公開環境で環境変数を分ける。
