# メール不要のログインID・パスワード認証

2026-09-23に実DBへmigrationを適用し、Edge Functionを配置。専用の一時アカウントで登録と再ログインを確認し、検証データは削除済み。ソースの既定値 `NEXT_PUBLIC_LOGIN_ID_ENABLED=false` は安全な初期値として維持し、対象環境のビルド時にだけ有効化する。

## 利用者向けの仕様

- ログインIDは英字から始まる半角英数字・`_`・`-`の4〜24文字。大文字小文字は区別しない。週次公開IDや表示名とは別で、他の利用者には表示しない。
- パスワードは半角の印字可能文字（スペースを含む）15〜72文字。空白だけは禁止。パスワードを切り詰めたり前後の空白を除去したりしない。
- メールアドレス・復旧コードは不要。IDやパスワードの紛失時は復旧できず、登録画面で同意を必須とする。
- 既存メールアカウントの自動移行・紐付けは行わない。既存の投稿を使う人は「メールを使う」からログインする。IDを新規登録すると別アカウントになる。
- 成功後は既存のSupabaseセッション保存・更新を使う。月が替わっても認証との対応と停止状態を保持し、公開プロフィールだけを更新する。
- パスワード変更・ID変更の画面は今回の範囲外。

## 構成と権限

Supabase Authのパスワード認証はメールまたは電話を識別子とするため、サーバー内でランダムな `UUID@login.reme.invalid` を生成して互換用識別子にする。実在するメールの所有確認ではなく、配信も復旧にも使わない。IDを識別子メールやuser_metadataに埋め込まない。

`reme_private.login_identities` にIDと識別子を保持し、ブラウザロールにはテーブル・対応取得RPCの権限を付与しない。パスワード保存・照合はSupabase Authが担当し、アプリのDBには保存しない。JWT等の標準的な認証資格情報は本人のブラウザに必要だが、公開プロフィール・業務RPCには内部情報を追加しない。

`reme-password-auth` Edge Functionが、入力検証→試行制限→ID解決→登録またはパスワード照合→既存 `reme_state` の停止検査→本人へのセッション返却を行う。共有の認証クライアントは使わない。レスポンスはセッショントークンのみでキャッシュ禁止。例外・入力・上流の詳細をログやエラーレスポンスに含めない。

事前ログインのエンドポイントなので、この関数に限り `verify_jwt=false` とし、入力された資格情報をサーバーで検証する。CORSは許可Originに限定するが認証境界とは見なさない。サービスキーをブラウザに渡さない。既存のメール確認設定を無効にしない。

試行制限は全体300回/分、クライアント30回/分、ID15回/15分。新規登録はさらに全体30回/時、クライアント5回/時。拒否時もカウントを確定する。転送IPは偽装・共有され得る補助情報で、全体・ID制限を独立して使う。IPとIDはSHA-256の値として試行テーブルに保存（匿名化とは見なさない）。期限から1日経った行は次の試行時に掃除する。

重複IDの登録で既存ユーザーを変更・削除しない。作成前にIDを予約し、通信失敗時にも予約を保持する。Auth作成だけが成功した場合は同じIDとパスワードでログインを試す。停止済みアカウントの拒否は維持するが、メール不要の新規登録による別アカウント作成まで防げるものではない。公開募集前に試行制限・運用負荷を確認する。

## 反映する際の順序

1. 対象がRE:MEのSupabaseプロジェクトであること、未適用migrationを確認する。既存のSQLをまとめて再実行しない。新規 `20260914033953_login_id_password.sql` のみを適用する。
2. `supabase/functions/reme-password-auth/` を同名のEdge Functionとして配置する。CLIではこのリポジトリから `supabase functions deploy reme-password-auth --project-ref <対象project-ref>` を使う。JWT設定は `supabase/config.toml` に記載済み。
3. ランタイムの `SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`、`SUPABASE_ANON_KEY` が利用可能なことを確認する（ホスト型Supabaseの既定環境変数）。値をチャット・Gitに貼らない。
4. 必要なら関数の `REME_AUTH_ORIGINS` に許可Originをカンマ区切りで設定する。既定は現在のSites URLのみ。ローカル検証時は `http://127.0.0.1:3100` を追加する。ワイルドカードは使わない。ローカルURLは本番検証後に外す。
5. `.env.local` の `NEXT_PUBLIC_LOGIN_ID_ENABLED=true` でローカルを再起動する。URL・Publishable keyは従来と同じ対象プロジェクトを使う。秘密のサービスキーを `.env.local` の `NEXT_PUBLIC_*` に入れない。
6. 専用テストアカウントで新規登録、ログアウト・再ログイン、同じブラウザでの復元、別端末、重複登録、誤ったパスワードを確認する。既存メールOTP、投稿保存、ブロックも確認する。本人の既存アカウントで破壊的な試験をしない。
7. 検証後にフロントを同じflagで再ビルドしてSitesへ反映する。静的ビルドなので変数変更だけでは公開画面は変わらない。停止する場合はflagをfalseにして再ビルド・反映する。アカウントやテーブルは削除しない。

## 検証済みと未検証

ローカルPGliteで全migration・権限・ID対応・期間境界・試行制限を検証。HTTPハンドラーは外部Authを模擬して登録・拒否・エラーの秘匿・ユーザートークンでの停止検査を検証。Denoの型検査・lint、Nextの型検査・有効flagでのビルドに成功。

実Supabase Authでの新規登録・トークン発行・同じIDによる再ログインまで確認済み。実ブラウザでの入力操作、ログアウト後の再ログイン、長期のセッション保持は未検証。
