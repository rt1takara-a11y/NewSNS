## 2026-09-13: 月次プロフィールのフォロー中・フォロワー一覧

- **決定:** 自分と他者のプロフィールに人数と一覧ダイアログを追加する。ブラウザ標準のdialogを使い、追加のUI依存は入れない。
- **DB:** 既存migrationと認証・保存RPCは変更せず、`reme_connections(target_public_id, expected_epoch)` と逆向き検索用indexを追加する。CLIで生成した `20260913021456_profile_connections.sql` に記録する。
- **権限:** privateテーブルを公開しないため、既存構成に合わせたsecurity definerを使用。空のsearch_path、JWT由来の閲覧者、認証済みロールへの限定grantを必須とする。対象が見えない場合は一律NOT_FOUND。
- **公開範囲:** 閲覧者と対象者の両方から見える今月の人だけを返す。非表示の人を人数から推測できないよう、人数は返された配列の長さとする。プロフィールの公開4項目のみを返す。
- **同期:** 既存の15秒同期とフォロー・ブロック変更に追随して再取得し、取得開始時のstateと一致する応答だけを表示する。遅れて届いた旧月・旧閲覧者・旧対象の応答は表示しない。通信失敗やSQL未適用時は人数不明として再試行を案内する。
- **制限:** 少人数の検証用に一覧を一括取得。ページングは今後の拡張。体験版では自分が作ったフォロー関係だけを表し、架空のフォロワー数は足さない。実環境へのSQL適用と実機操作確認は別途必要。

## 2026-09-12: 月次公開IDのプロフィール画面を既存APIに接続
- **決定:** `/user/?id=<月次公開ID>` を静的ルートとし、投稿・返信・ユーザー一覧の名前/アイコンから開く。自分の編集画面 `/profile` は維持する。
- **理由:** static exportと既存のSites構成を保ち、毎月発行されるIDをビルド時に列挙する必要をなくす。URL・プロフィール表示には内部アカウントやメールを使わない。
- **アクセス:** 認証済みの最新スナップショットで対象が見える場合のみ表示。ブロック管理一覧からプロフィールを復元しない。旧月・停止・ブロック・不明な対象は同じ非表示画面にする。
- **範囲:** 既存RPCでフォロー/解除を保存。投稿表示は全体最新100件に含まれる対象者の投稿に限定し、画面に明記。DB変更と実環境への適用は行わない。

## 2026-09-08: メールOTP・保存・権限チェックをSupabaseに集約
- **決定:** 既存Next.jsは維持。メールOTPとPostgreSQLのprivateスキーマ＋認証済みRPCを追加。新依存はsupabase-js、検証用にPGlite。
- **理由:** メールログイン要件を守り、ChatGPTアカウント認証への置き換えや別サーバー管理を避ける。D1ではなく認証との対応を同じDBで管理する。
- **期間:** サーバーの日本時間とリセット世代を用いる。古い画面からの書き込みは拒否。期間が切り替われば前月データをRPCで取得できない。
- **管理:** 通報・ブロック・停止・非表示・保守関数を実装。管理関数はDB所有者専用。運営UIは未実装。
- **保存:** 古い公開データと通常の通報は暫定90日。保全対象の通報は除外。公開前に保持方針を確認する。
- **状態:** 所有者のSupabase接続・SMTP設定が未提供。未接続時は明示した体験版を維持。本運用開始とは扱わない。

## 2026-09-08: サービス名をRE:ME（リミー）に決定
- **決定:** ユーザーがRE:MEを選択。表示名・ページタイトル・事業資料を統一する。
- **意味:** 毎月、自分を始め直す。コピーは「毎月、あたらしい自分に。」。
- **運用:** GitHubリポジトリ名と既存プレビューURL、npmパッケージ名は技術的な識別子として維持する。

## 2026-09-08: 操作可能な本人限定プレビュー
- **決定:** Next.jsのstatic exportとtrailingSlashを有効にし、静的ホスティング可能な形で試作品を配布する。
- **理由:** 現行4画面はブラウザ内モックで完結し、サーバーやDBを追加せず確認できるため。
- **互換性:** devラッパーでプレビュー環境のhost/strictPort引数をNext.jsへ変換する。通常のnpm run devも維持。
- **制限:** API・認証・DB導入時にはstatic export構成を再検討する。再読み込みでデータが初期化される。

## 2026-09-08: UIをチャコールとライムのテーマに統一

- **決定:** 暗色背景、ライムの操作色、線画アイコン、PCのサイドナビとスマホの下部ナビを採用。月表示と説明をPCの補助欄へ配置。
- **理由:** テキストの読みやすさを優先しつつ、月ごとに新しくなるSNSの個性を表現する。
- **範囲:** 4画面と共通コンポーネントのUI。既存のメモリストア・リセット処理・依存関係は変更しない。アバターの絵文字選択は維持。
- **公開ID:** 画面上のID文字列を月次の説明に置換。データ構造は維持し、再特定防止を保証する本番API・認証は未実装。
- **テーマ:** OS設定によらず暗色で統一。フォームラベル、選択状態、フォーカス、セーフエリア、動きを減らす設定に対応。

## 2026-09-07: 試作品の技術スタックは Next.js + TypeScript

- **決定:** フェーズ1の試作品は Next.js（App Router）+ TypeScript で作る。データは保存せずブラウザ内モックで動かす。スタイルは素のCSS。アイコンは絵文字ピッカー。
- **理由:** 少人数検証に向き、スマホブラウザで動くWeb版を最小コストで作れる。試作品では「見た目と流れ」の確認が目的なので、DB・認証はフェーズ2に回す。
- **トレードオフ / 却下した案:** 画像アップロードは後回し（絵文字で代替）。永続化なし（再読み込みで初期化）。

## 2026-09-07: 公開IDは運営内部だけで管理し、利用者同士は追跡できない

- **決定:** 公開IDも毎月変更する。内部IDは画面・公開URLに一切出さない。利用者は前月の人をサービス内でたどれない。
- **理由:** 「毎月の出会い直し」を徹底するため。ユーザーがID検索で再フォローできる案もあったが、それだと再特定ができてしまうため不採用。約束するのは「サービス内で前月のアカウントをたどれないこと」まで。
- **トレードオフ:** 気の合う人を失う寂しさは強くなる。これは検証すべき仮説として受け入れる。

## 2026-09-07: 継続アカウントと月次公開プロフィールを分離

- **決定:** 「継続するログイン用アカウント（内部）」と「毎月消える公開プロフィール」をデータ構造として分ける。
- **理由:** 同じメールでログインできつつ、利用者からは毎月新しい人物に見える、という核となる体験を実現するため。
